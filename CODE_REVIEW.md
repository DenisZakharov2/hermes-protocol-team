## 3. Фокус: Веса качества

### W2 🟠 Взвешенная сумма молча не проверяется при неполном breakdown

`scripts/validate-json.mjs:117-131` (`evaluationReportInvariantErrors`):

```js
for (const [axis, weight] of Object.entries(QUALITY_WEIGHTS)) {
  if (typeof breakdown[axis] !== 'number') {
    complete = false;
    break;          // ← проверка просто пропускается
  }
  expected += breakdown[axis] * weight;
}
if (complete && ...) { errors.push(...) }
```

Если в `QUALITY_WEIGHTS` появится ось, которой нет в `score_breakdown` (дрейф между `definitions.schema.json` и `evaluation_report.schema.json`), проверка формулы `overall_score` **тихо отключится**, и все примеры останутся «валидными». Это самый опасный режим отказа для инварианта-стража: он должен падать, а не замолкать.

**Рекомендация:** при `complete === false` пушить ошибку `score_breakdown is missing axis "<axis>" required by QualityWeights`.

### W1 🟡 Нормативный источник весов — `examples[0]` внутри JSON Schema

Веса читаются из `schemas/common/definitions.schema.json` → `definitions.QualityWeights.examples[0]` (`validate-json.mjs:23-32`, `generate-docs.mjs:150-158`). Плюсы: действительно один источник для валидатора и генератора docs, сумма проверяется с float-допуском. Минусы:

- `examples` в JSON Schema — документационное поле: оно **не валидируется** самой схемой, IDE/плагины и автогенераторы могут его перезаписать или удалить без каких-либо сигналов от Ajv.
- Проверку суммы весов (`Σ = 1 ± 0.0001`) выполняет только `validate-json.mjs`; `generate-docs.mjs` отрендерит в docs любые веса без проверки.

**Рекомендация (минимальная):** продублировать проверку суммы в `generate-docs.mjs`. **Оптимальная:** вынести веса в отдельный файл `schemas/common/quality_weights.json`, подключить через `$ref`/`const`, а `examples` оставить только для документации.

### W3 🟡 Список пяти осей продублирован в четырёх местах без кросс-проверки

1. `definitions.schema.json` → `QualityWeights.properties` + `required`
2. `evaluation_report.schema.json` → `score_breakdown.properties` + `required`
3. `scripts/generate-docs.mjs:162-168` → хардкод `axisLabels`
4. `skills/quality-evaluator/SKILL.md:41-42` → проза «25 %»

Если ось переименуют в схеме весов: `generate-docs.mjs` молча пропустит её в таблице (итерация идёт по `axisLabels`, а не по ключам весов), а проза в SKILL.md разойдётся с фактами. **Рекомендация:** добавить в `validate-json.mjs` кросс-чек «ключи `QualityWeights` ≡ свойства `score_breakdown` ≡ ключи `axisLabels`»; в `generate-docs.mjs` итерировать по ключам весов.

### W4 🟡 CI проверяет свежесть только половины сгенерированных docs

`.github/workflows/validate.yml`, job `docs`: `git diff --exit-code -- docs/schemas-reference.md`. Но `generate:docs` обновляет и таблицу весов в `docs/04-quality.md`. Дрейф таблицы весов в документации пройдёт CI. **Рекомендация:** `git diff --exit-code -- docs/`.

### W5 🟢 Допуск 0.05 адекватен, но не покрыт по границе

Формула с tolerance 0.05 задокументирована (CHANGELOG), но в фикстурах нет граничного кейса (например, расхождение 0.04 — должно пройти, 0.06 — отклониться). Низкий приоритет.

## 4. Фокус: Двойная валидация в self-test

Архитектура корректная: слой 1 — JSON Schema (Ajv, `strict`, `allErrors`), слой 2 — регламентные инварианты; self-test требует, чтобы негативная фикстура была **schema-валидной** и была **отклонена инвариантом** с ошибкой, совпадающей с `expectedErrorPattern` из манифеста. Все 10 фикстур сейчас проходят. Проблемы:

### V1 🟠 Первый слой двойной валидации не тестируется в принципе

`runSelfTest` (`validate-json.mjs:434-455`): фикстура, не прошедшая схему, помечается ⚠️ и засчитывается как failure. В `manifest.json` нет поля уровня ожидаемого отказа (`failLayer: "schema" | "invariant"`). Следствие: невозможно написать негативный тест для слоя схемы (например, `overall_score = 150`, неизвестный `risk_level`), а значит «двойная валидация» покрыта self-test-ом ровно наполовину.

**Рекомендация:** добавить в манифест поле `failLayer` и ветку «фикстура обязана упасть на схеме».

### V2 🔴 4 из 10 `artifact_type` молча пропускают валидацию вложенного артефакта

`eval_request.schema.json` объявляет enum из 10 значений `artifact_type`, но `ARTIFACT_SCHEMA_BY_TYPE` (`validate-json.mjs:57-64`) маппит только 6. Для `presentation`, `executive_summary`, `analytical_memo`, `market_research_whitepaper` инвариант `evalRequestInvariantErrors` (`validate-json.mjs:240-244`) делает `return errors` с пустым списком — **без предупреждения**. `artifact_data` таких запросов не валидируется ни схемой, ни инвариантом: двойная валидация деградирует до одинарной, и это не видно ни в выводе, ни в CI.

**Рекомендация:** либо пушить ошибку `no artifact schema mapping for artifact_type "<x>"`, либо при старте сверять множество `ARTIFACT_SCHEMA_BY_TYPE` с enum из `eval_request.schema.json` (и падать при расхождении).

### V3 🟡 Нет валидации самого манифеста

- Фикстура, чья схема не имеет инвариант-функции, не может быть отклонена — она гарантированно упадёт с «should have been rejected but passed». Это обнаружится только в рантайме, непонятным сообщением.
- `new RegExp(expectedPattern)` без `try/catch`: опечатка в манифесте уронит весь self-test стек-трейсом.
- Паттерны не заякорены и матчятся по склейке **всех** ошибок — возможен ложный «успех» по посторонней ошибке (у `project-id-mismatch.json` сообщение содержит 5 посторонних ошибок схемы `artifact_data`).

**Рекомендация:** пре-валидация манифеста (схема существует, check зарегистрирован, паттерн компилируется), якоря `^...$` в паттернах.

### V4 🟡 Пробелы в покрытии негативных фикстур

Нет фикстур на: `duplicate stage_code` (execution_plan), approval-инвариант execution_plan (`approval-flag-mismatch` есть только для orchestration_output), `CRITICAL` + `APPROVED_WITH_RESERVATIONS`, отсутствие оси в `score_breakdown` (см. W2), `artifact_type` без маппинга (см. V2). Self-test зрелый, но инварианты покрыты неравномерно.

### V5 🟢 Косметика self-test

- Self-test выполняется **после** success-сообщений основной валидации («All 21 examples are valid…») — при падении self-test вывод выглядит противоречиво.
- `let failed` в `runSelfTest` затеняет модульную `failed`.
- `npm run validate:self-test` повторно прогоняет всю основную валидацию перед self-test (двойная работа, ~удвоение времени шага).

## 5. Прочие находки

### F1 🔴 Подтверждённый падающий тест: snapshot `sync-version`

`npm test` → `tests/snapshot/sync-version.test.mjs:149-159`, тест `patch bump (3.0.1 -> 3.0.2) > should update all 21 files` — **FAIL**.

Первопричина: тест жёстко зашивает целевую версию `3.0.2`, которая после коммита `0f058ce chore: bump version to 3.0.2` **равна текущей версии репозитория**. `sync-version.mjs` при совпадении версий не меняет контент → все 20 паттернов считаются «Pattern not matched» → `process.exit(1)` → `execSync` бросает. Воспроизведено в чистой копии репо: `Summary: 1 files updated, 20 issues`, exit 1. Тест будет красным до следующего релиза, потом сломается снова на следующей версии.

**Рекомендация:** в тесте вычислять целевую версию динамически из `package.json` (patch + 1) вместо константы; либо в `setupTempRepo` принудительно откатывать версию копии на предыдущую.

### F2 🟠 CI не запускает vitest

`.github/workflows/validate.yml` выполняет только `npm run validate`. Шага `npm test` нет, поэтому F1 не ловится в PR и вообще нигде не ловится. **Рекомендация:** добавить шаг `npm test` (с учётом ~60 c на `npm ci` во временных репо — стоит вынести snapshot-тесты в отдельный job с кэшем).

### F3 🟡 `sync-version.mjs` не идемпотентен и сигнализирует «успех» через хак

Повторный запуск с той же версией — exit 1 (это и есть триггер F1). Для SECURITY.md сделан специальный хак `securityPatternMatched` («паттерн сработал, даже если контент не изменился») — симптом того, что критерий успеха «контент изменился» неверен. **Рекомендация:** считать успехом «паттерн найден» (совпадение), а не «контент изменился»; одинаковая версия → no-op с exit 0 и предупреждением.

### F4 🟢 Плейсхолдеры вместо реальных CVE

`package.json` → `_overrides_comment`: «CVE-2024-XXXX» — не настоящие идентификаторы; ссылка на несуществующие CVE в файле безопасности вводит в заблуждение. Лучше указать реальные ID или описать причину пина без псевдо-ссылок.

### F5 🟢 Относительные пути в скриптах

`validate-json.mjs` / `check-mermaid.mjs` / `init-memory.mjs` используют пути относительно cwd (`'schemas'`, `'examples'`). `npm scripts` это гарантируют, но прямой запуск `node scripts/validate-json.mjs` из другого каталога даст малопонятные ошибки. Низкий приоритет.

## 6. Что сделано хорошо

- **Единый нормативный источник весов** с проверкой суммы и float-допуском; генератор docs и валидатор читают одно и то же.
- **Self-test с манифестом негативных фикстур** и проверкой текста ошибки — правильный подход, редко встречается в doc-репо.
- **Содержательные инварианты**: DAG без циклов/дыр/forward-ссылок, агрегация рисков, `approved_by_human` ↔ вердикт, `passed` ↔ порог — это реальная защита контрактов, а не формальность.
- **Настоящий парсер Mermaid** (`mermaid.parse`, `securityLevel: 'strict'`) вместо эвристик; корректный подъём jsdom.
- **Pinned Actions по SHA**, `concurrency`, CodeQL по расписанию, аккуратный SECURITY.md с проверкой таблицы поддерживаемых версий в CI.
- Сквозной `project_id` по всем примерам — простая и эффективная проверка целостности «одной истории».
