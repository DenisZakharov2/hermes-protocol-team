## 1. Executive Summary

Репозиторий представляет собой **зрелую, хорошо проработанную спецификацию** мультиагентного протокола для банковской/финансовой сферы РФ. После предыдущего независимого аудита (v3.0.2 → v4.0.0) большинство критических и высоких проблем закрыты: HITL-байпасы, path traversal, SSRF через research sources, расхождения версий, corruption в sync-version, отсутствие npm test в CI и т.д.

**Текущее состояние:** высокое качество схем (строгие `additionalProperties: false`, единые определения, инварианты арифметики и quality score), сильный валидатор с self-test + negative fixtures, профессиональный CI (audit, CodeQL, docs regeneration check, SECURITY.md table check), хорошая документация и single source of truth.

**Основные residual-риски и зоны роста:**
- Ограниченное покрытие unit/integration-тестами сложной логики инвариантов (помимо self-test).
- Санитизация пользовательского ввода и защита от prompt injection остаются преимущественно декларативными (в скиллах), без reference implementation.
- Отсутствие локального runtime-симулятора/оркестратора для end-to-end проверки протокола.
- Жёсткий pin Node.js ≥22.22.2 без удобного локального tooling (нет `.nvmrc`).

**Общая оценка:** 8.5/10. Репозиторий готов к production-использованию как спецификация и контрактный слой. Основные улучшения — в области тестируемости, runtime-инструментов и усиления защитных механизмов на границе с LLM.

## 2. Сильные стороны

- **Строгие контракты.** Все основные артефакты имеют JSON Schema с `additionalProperties: false`, чёткими enum, pattern (ProjectId `^[A-Z0-9_]+$`), format, min/max. Общие типы вынесены в `schemas/common/definitions.schema.json`.
- **Single Source of Truth.** 
  - Обязательный пайплайн (11 этапов) — `definitions.MandatoryPipeline.const` в `execution_plan.schema.json`.
  - Веса качества — только `schemas/common/quality-weights.json`.
  - Allow-list доменов — `schemas/common/source-allowlist.json`.
  - Список агентов — enum `AgentId`.
- **Мощный валидатор** (`scripts/validate-json.mjs`):
  - Схема + глубокие инварианты (DAG, HITL, self-healing counters 1→2→3 + escalation, financial CoF/NIM/NII, RICE, quality score weighted + CRITICAL stop-кран, path matching `cases/{project_id}/...`, SSRF-защита).
  - Self-test с valid/invalid fixtures.
  - Defense-in-depth (HTTPS, no userinfo, no IP literals, private ranges, allow-list host/subdomain).
- **Безопасность и CI:**
  - Pinned Node 22.22.2 (с учётом CVE в зависимостях).
  - Actions by commit hash.
  - `npm audit --audit-level=high` в CI.
  - CodeQL (security-extended).
  - Dependabot (с разумными ignore для mermaid/markdownlint).
  - Проверка актуальности `docs/schemas-reference.md`.
  - Проверка таблицы поддерживаемых версий в SECURITY.md.
- **Документация и процесс.** Конституция, WORK_PLAN, подробные скиллы, примеры, CHANGELOG (Keep a Changelog), CONTRIBUTING, SECURITY.md с private vulnerability reporting.
- **Предыдущий аудит закрыт.** AUDIT_HANDOFF.md фиксирует закрытие блоков 0–4 (corruption, HITL, memory paths, legal/quality invariants, CI hygiene).

## 4. Проблемы безопасности

| Уровень | Проблема | Статус | Комментарий |
|---------|----------|--------|-------------|
| Закрыто | Path traversal (`../`) в `artifact_root` / `lessons_indexed_to` | ✅ | Инвариант + schema pattern + negative fixtures. |
| Закрыто | SSRF / private IP / IP literals / non-HTTPS в `research_output.sources[].url` | ✅ | Allow-list + defense-in-depth в валидаторе. |
| Закрыто | HITL bypass (COMPLETED без human approval) | ✅ | Cross-check с `orchestration_output.stage_gate_history`. |
| Закрыто | Self-healing без эскалации на 3-й попытке | ✅ | Инвариант + pending escalations. |
| Residual | Prompt injection / jailbreak через user_prompt | Medium | Длина ограничена, поле `sanitized_user_prompt` есть. Реальная фильтрация — на стороне runtime. |
| Residual | Зависимости (dev) | Low | Overrides на известные GHSA/CVE, audit в CI, Dependabot. |
| Residual | Mermaid parsing | Low | `securityLevel: 'strict'` + jsdom. |
| Info | Скрипты валидации | Low | Читают только локальные файлы, нет динамического выполнения пользовательского ввода. |

**Рекомендации по безопасности:**
- Добавить reference sanitizer.
- В runtime (Hermes Agent) обязательно применять allow-list + HTTPS-only + timeout при реальных HTTP-запросах исследователя.
- Рассмотреть подпись/хеш артефактов при передаче между агентами (для защиты от подмены в shared memory).

## 5. Предложения по улучшению

### 5.1. Надёжность и тестируемость
- **Выделить pure-функции инвариантов и покрыть их unit-тестами (vitest).**  
  *Зачем:* сложная логика (финансовые формулы CoF/NIM/NII, последовательность self-healing, расчёт weighted score, HITL-проверки) сейчас проверяется только внутри большого self-test. При любом рефакторинге легко сломать поведение незаметно.  
  *Что даст:* быструю и изолированную проверку каждого правила, уверенность при изменениях, возможность безопасно развивать валидатор.

- **Добавить integration-тест: «сгенерировать минимальный набор артефактов по обязательному пайплайну → прогнать через валидатор».**  
  *Зачем:* unit-тесты проверяют куски, но не весь поток «план → артефакты → cross-checks между ними».  
  *Что даст:* гарантию, что обязательный пайплайн и связи между артефактами (project_id, пути, статусы гейтов) работают как единое целое.

- **Расширить negative fixtures (unicode в project_id, очень длинные строки, граничные финансовые значения, пустые массивы где minItems > 0).**  
  *Зачем:* текущие fixtures покрывают основные случаи, но не все граничные и «грязные» входные данные.  
  *Что даст:* более надёжную защиту от неожиданных ошибок в реальных запусках агентов.

### 5.2. Функциональность и tooling
- **CLI для runtime:** `npx hermes-validate <artifact.json>` (или отдельный пакет), который агенты могут вызывать перед записью артефакта.  
  *Зачем:* сейчас валидатор — это скрипт репозитория. Агентам в runtime неудобно и небезопасно полагаться только на «память» скилла.  
  *Что даст:* возможность агенту (или оркестратору) мгновенно проверить артефакт перед сохранением и сразу получить понятные ошибки. Снижает количество итераций self-healing.

- **Локальный симулятор оркестратора** (минимальный): принимает `execution_request.json`, проходит по MandatoryPipeline, вызывает mock-воркеров (или реальные LLM), пишет flight logs и проверяет инварианты на каждом шаге.  
  *Зачем:* сейчас проверить полный сценарий можно только вручную или в настоящем Hermes Agent.  
  *Что даст:* быструю отладку изменений в скиллах, схемах и инвариантах без полного развёртывания системы. Ускоряет разработку и регрессионное тестирование.

- **Скрипт синхронизации «skill required outputs ↔ schema required fields».**  
  *Зачем:* скиллы и схемы развиваются отдельно. Легко забыть добавить поле в схему или описать его в скилле.  
  *Что даст:* автоматическое обнаружение рассинхронизации на этапе CI. Меньше сюрпризов при работе агентов.

- **Генерация TypeScript-типов из JSON Schema (для строгой типизации в runtime, если Hermes Agent на TS/JS).**  
  *Зачем:* агенты и оркестратор работают с JSON-артефактами. Без типов ошибки в структуре обнаруживаются только в рантайме.  
  *Что даст:* автодополнение, проверку типов на этапе разработки и меньше runtime-ошибок.

### 5.3. Безопасность
- **Reference-модуль санитизации `user_prompt` → `sanitized_user_prompt` (strip control chars, ограничение вложенных инструкций, length, encoding).**  
  *Зачем:* сейчас поле `sanitized_user_prompt` есть, но как именно чистить вход — не определено. Каждый runtime реализует по-своему (или не реализует).  
  *Что даст:* единый, проверяемый эталон очистки. Снижает риск prompt injection и делает поведение предсказуемым.

- **Документировать и, по возможности, формализовать политику обновления `source-allowlist.json`.**  
  *Зачем:* allow-list — ключевой элемент защиты от SSRF. Без чётких правил его легко расширить небезопасным доменом.  
  *Что даст:* контролируемое и прозрачное расширение списка разрешённых источников. Проще проводить аудит безопасности.

- **Добавить в flight_log обязательное поле `sanitization_applied: true` + hash исходного prompt (опционально).**  
  *Зачем:* сейчас нельзя достоверно проверить, была ли применена санитизация.  
  *Что даст:* возможность аудита и постфактум-анализа инцидентов. Повышает доверие к логам.

### 5.4. Оптимизация и поддерживаемость
- **Добавить `.nvmrc` + раздел в README.**  
  *Зачем:* engines требует Node ≥22.22.2, но локально это неудобно переключать.  
  *Что даст:* команда `nvm use` сразу ставит нужную версию. Снижает порог входа для новых разработчиков и агентов.

- **Вынести tolerance и некоторые magic numbers (3 итерации self-healing, 5000 chars) в единый конфиг рядом с quality-weights.**  
  *Зачем:* числа разбросаны по схемам, валидатору и документации. Менять их опасно и легко забыть где-то.  
  *Что даст:* единое место правды. Проще менять политику (например, увеличить лимит self-healing) согласованно.

- **Рассмотреть schema versioning (`$id` с версией или поле `schema_version` в корне артефактов) для более плавной эволюции контрактов.**  
  *Зачем:* при breaking changes (как было при переходе на относительные пути) сложно поддерживать старые артефакты.  
  *Что даст:* возможность постепенно мигрировать и явно понимать, какая версия контракта используется.

- **Автоматическая генерация таблицы stage_code / owner / approval_required из MandatoryPipeline в документацию (частично уже есть через generate-docs).**  
  *Зачем:* таблица этапов дублируется в Конституции, скиллах и схемах.  
  *Что даст:* устранение риска расхождения документации с реальным пайплайном.

### 5.5. Наблюдаемость и операционка
- **Стандартизировать дополнительные поля в `flight_log.entries` (duration_ms, tokens_used, model, retry_reason) — сейчас они свободные.**  
  *Зачем:* сейчас каждый агент пишет логи по-своему. Сложно агрегировать и анализировать.  
  *Что даст:* единообразные метрики. Можно строить дашборды, считать стоимость, находить узкие места.

- **Добавить в orchestration_output агрегированные метрики (First-Time Right Rate, количество self-healing циклов, время на этап).**  
  *Зачем:* сейчас эти показатели можно посчитать только вручную из логов.  
  *Что даст:* быструю оценку качества работы команды агентов после каждого проекта. Упрощает AAR и постоянное улучшение.

## 6. Приоритеты

| Приоритет | Действие | Ожидаемый эффект |
|-----------|----------|------------------|
| Высокий | Unit-тесты на ключевые инварианты + расширение self-test | Снижение риска регрессий |
| Высокий | Reference sanitizer + документация для runtime | Снижение prompt injection риска |

## 7. Заключение

Репозиторий **Hermes Protocol Team v4.0.0** — качественная, хорошо защищённая и продуманная спецификация мультиагентной системы. Критические проблемы предыдущего аудита закрыты, single source of truth соблюдается, валидатор строгий и многоуровневый.

Основные точки роста лежат в области **тестируемости сложной бизнес-логики инвариантов**, **практической реализации защитных механизмов на границе с LLM** и **создания runtime-инструментов**, которые позволят агентам и разработчикам легче соблюдать контракты.

Репозиторий можно рекомендовать как основу для production-команды ИИ-агентов в регулируемой финансовой сфере РФ при условии реализации reference-санитизации и усиления тестового покрытия.
